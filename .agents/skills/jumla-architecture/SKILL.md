# ذاكرة معمارية جملتي (Jumla Architecture Skill)

> **تحذير لكل وكيل:** هذا الملف هو الذاكرة المستمرة للمشروع عبر الجلسات. اقرأه كاملاً قبل البدء بأي عمل.
> كل إنجاز أو قرار يوثق هنا **بالإلحاق** (append-only) ولا يُمسح القديم إطلاقاً.

---

## 1. هوية النظام والمواصفات التقنية
- **المنصة:** نظام تجارة الجملة المتكامل (العراق).
- **البيئة التقنية:** Next.js 16.2.6 (App Router + Turbopack) + React 19.2.4 + Tailwind CSS v4.
- **قاعدة البيانات:** Supabase Cloud (باقة مجانية بدون نسخ احتياطي — كل تغيير SQL يجب أن يكون مدروساً وموثقاً).
- **الاستضافة والنشر:** Vercel متصل بـ GitHub Repo (`https://github.com/muslim1972/jumla.git`) — النشر أوتوماتيكي عبر `main`.

---

## 2. الدرع الواقي وحارس الطابوق
- **دستور المشروع:** `AGENTS.md` في جذر `D:\jumla\`.
- **أمر فحص الحارس:**
  ```powershell
  node scripts/verify-bricks.mjs
  ```
- **فحص الأنواع قبل الاعتماد:**
  ```powershell
  npx tsc --noEmit
  ```
- **بناء الإنتاج قبل الدفع:**
  ```powershell
  npm run build
  ```

### [2026-10-12] DEC-02: تصميم نظام الطرح المخزني المشروط بالرقابة الثنائية (Dual-Approval Deduction)

- **القرار والتنفيذ:**
  1. إنشاء جدول `warehouse_deduction_requests` مع فهارس وسياسات RLS، ودالة RPC ذرية `warehouse_process_deduction_decision`.
  2. إضافة تبويبة "طرح من المخزن" في نافذة الصنف (`WarehouseItemDialog`) بموقع المستطيل الأحمر، وإلزام اختيار الموظف الشاهد إن وجد أو توجيه الطلب للتاجر إن كان موظفاً وحيداً.
  3. حماية تبويبة "حركة مخزنية" ومنع الإخراج المباشر أو تسوية الجرد للموظفين لإلزامهم بمسار طلب الطرح المعتمد.
  4. بناء تبويبة "طلبات الطرح" في لوحة المخازن (`WarehouseHub`) مع شارات التنبيه وأزرار اتخاذ القرار التفاعلية (تأييد/اعتماد/رفض) وإشعارات لحظية لجميع الأطراف.
  5. اجتياز حارس الطابوق (157/157 ملف بنسبة 100%)، وفحص الأنواع الصارم (0 أخطاء)، وبناء الإنتاج بنجاح تام.

### [2026-10-13] DEC-03: إصلاح استعلام حركات المخزن (PostgREST PGRST201) وتوحيد وحدات العرض
- **الدافع:** اختفاء حركات المخزن المعتمدة من تبويبة "آخر الحركات" للصنف ومن "دفتر الحركات" رغم ثبوتها في قاعدة البيانات.
- **التشخيص والحل:**
  1. كشف خطأ `PGRST201` بسبب وجود مفتاحين أجنبيين بين `warehouse_movements` و `profiles` (`merchant_id` و `performed_by`)، وتم حله بتحديد العلاقة صراحة: `actor:profiles!warehouse_movements_performed_by_fkey(full_name)`.
  2. إضافة فحص وتسجيل أخطاء `movementsRes.error` بدلاً من ابتلاعها بصمت.
  3. مواءمة كميات ورصيد الحركات في نافذة الصنف مع وحدة العرض الحالية المعتمدة (كيس/كارتون) باستخدام `baseToDisplay` لتتطابق أرقام الحركة مع رصيد الترويسة، وتمييز شارة "طرح معتمد" وفك اختصار الملاحظات لقراءتها بالكامل.

### [2026-10-14] DEC-04: مخطط تعزيز Pool بمرشحين من مصادر مفتوحة

- اعتماد المطابقة بالاسم الموحّد ثم الوصف، وعدم استخدام الباركود كمفتاح هوية. الترحيل المقترح يزيل فهرس الباركود الفريد، ويضيف فهرساً فريداً للاسم والوصف بعد فحص التعارضات القديمة.
- حفظ المصدر والترخيص مع المرشح والمادة، وإظهار الإسناد في إدارة المواد وصفحات المنتجات. الصور الخارجية محصورة بمضيفات Open Facts المعروفة.
- لا يكتمل التفعيل قبل تطبيق `scripts/catalog/09-external-catalog-import.sql` يدوياً على Supabase بعد مراجعة نتائج فحص التكرار والسياسات الفعلية. لم يُنفذ الترحيل على قاعدة البيانات أثناء هذا العمل.
- ملحق التنفيذ: اعتماد المرشح وإدخاله إلى Pool ذري عبر RPC مع قفل السجل، وحد البحث 10/دقيقة لكل مدير، وإقرار إداري صريح بالتزامات ODbL وCC BY-SA. أزيلت مطابقة الباركود من إدخال المخزن وأزيل فهرسه الفريد عبر الترحيل؛ يجب تنفيذ الترحيل قبل تفعيل التطبيق.

### [2026-10-14] DEC-04 ملحق: التوافق مع تكرارات Pool التاريخية
- كشف فحص قاعدة الإنتاج أربع مجموعات مكررة بالاسم والوصف؛ لا ترتبط سجلاتها حالياً بمنتجات التجار، لكن بعضها يختلف في الصورة أو وحدة البيع، لذلك لا تحذف ولا تدمج تلقائياً.
- استُبدل شرط الفهرس الفريد الذي كان يوقف الترحيل كله بفهرس بحث غير فريد وحارس ذري داخل RPC باستخدام advisory transaction lock ثم فحص الاسم والوصف. هذا يسمح بإكمال الترحيل مع إبقاء البيانات التاريخية، ويمنع قبول التكرار الجديد عبر مسار الاستيراد.
- بعد تحديث الترحيل 09، يعاد تشغيله ثم 10 عند الحاجة. لا يكتمل تفعيل البحث حتى نجاحهما والتحقق من جداول الكتالوج وصلاحياتها.

### [2026-10-17] DEC-05: حصر الاستيراد المفتوح بمنتجات موسومة للعراق
- تجربة البيانات أثبتت أن نتائج البحث العامة لا تمثل السوق العراقي بما يكفي. أضيف فلتر بلد العراق إلى استعلامات Open Facts، ثم تحقق خادمي إلزامي من `countries_tags` قبل حفظ أي مرشح؛ لن تُقبل نتيجة عالمية لا تحمل وسم العراق.
- لا تُملأ خانة الباركود المستورد إلا إذا اجتاز GTIN فحص التنسيق والمجموع الاختباري، لأن الباركود اختياري وقد يؤدي الرقم غير الصالح إلى رفض الحفظ.
- تحمل واجهة الاعتماد أقسام المواد القائمة، وتلزم برفع صورة بديلة إذا كانت صورة المصدر غائبة أو تعذر تحميلها. توثق أخطاء الحفظ في سجل الخادم.
- هذا القيد يعكس بيانات المصادر المفتوحة الموسومة للعراق، ولا يضمن وحده توافر المخزون لحظياً؛ تبقى مراجعة المدير شرطاً قبل إدخال المادة إلى Pool.
- لتغطية المرشحين المحفوظين من البحث العالمي السابق، أضيف `market_country`؛ السجلات القديمة `unverified` وتُحجب عن الواجهة ويرفضها الخادم وRPC حتى إعادة البحث والتحقق. يتطلب ذلك تطبيق `scripts/catalog/11-iraq-market-verified-candidates.sql` قبل نشر نسخة التطبيق.

### [2026-10-17] ملحق DEC-05: توضيح توقف المصدر 503
- توثيق Open Food Facts ينص على أن حد البحث 10 طلبات في الدقيقة لكل IP وقد ينتج عنه HTTP 503. وحيث أن خادم التطبيق قد يجمع طلبات أكثر من مدير تحت IP واحد، لا يكفي حد التطبيق المحسوب لكل مستخدم لتجنب هذا الرد.
- تعرض واجهة المدير عند 503 تنبيهاً يحدد المصدر واحتمال الحد المشترك، ويوجه للانتظار دقيقة قبل محاولة واحدة؛ لا يعيد الخادم المحاولة تلقائياً حتى لا يزيد الضغط على المصدر.

### [2026-10-17] تصحيح ملحق 503
- لا يجوز استنتاج أن 503 سببه تجاوز حد IP من لقطة شاشة؛ توثيق Open Food Facts يذكر أيضاً قيوداً عامة مستقلة عن IP وخيارات صيانة/حمل الخادم.
- أزيل الجزم بفرضية حد IP من رسالة المستخدم. يسجل الخادم معرّف تشخيص ورؤوس المصدر غير الحساسة (مثل `Retry-After` و`Server` وrequest ID) عند 503 لتمييز الأسباب من سجل الاستضافة بعد حدوثه.
